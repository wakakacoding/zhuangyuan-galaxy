# 状元星河 · 数据契约 v1

生效：2026-10-20（T05 定稿）。实现位置：`src/lib/schema.ts`；守卫：`scripts/build-data.ts` §7c；测试：`scripts/data-contract.test.mjs`。
兼容基线：commit `688b18f` 的全部既有数据。**本契约只新增可选字段与语义，不改写任何史料。**

**v1.1（2026-10-23，T02 裁定落地）**：

- 出处等级新增 **A−（权威学术编纂）**：非一手、但为该领域整理基准（如《登科记考》）。数据值 `A-`，展示 `A−`。A− 与 A 同样要求 `juan+quote` 才能标 `check: quoted`。
- `rank_detail` **删除 schema 默认值**：仅在核到名次明文时写入；缺省 = 未核到名次（原默认值使 656/656 携带断言，其中 556 人无出处，且「一甲」用于唐五代属时代错置）。
- 新增守卫 §7d「断言强度 ≤ 引文强度」：夺魁事件所挂出处已核（quoted）而引文无「第一/状元/榜首」类名次明文、且同人无其他已核引文支撑时构建失败；已标 disputed 者降为警告（异说披露状态）。
- stats.json `contract_version` 升为 **1.1**。

## 一、为什么要有这份契约

旧 schema 把三件不同的事混在一起：

1. **整理状态**（本站做到哪一步）与**身份争议**（史料本身有异说）共用一个 `research_status` 枚举，取值里同时出现 `uncompiled` / `compiled` / `disputed`；
2. 仕途只剩一个 `final_office` / `final_category`，"最高官""末任""去向""死亡"四种事实挤在同一格；
3. 缺字段既可能表示"没整理"，也可能表示"查过没找到"，前端与统计无法区分。

v1 的目标是让**"没做""做了但没找到""有值"**三种状态在数据层就分开，并且**禁止用旧字段自动推导新字段**。

## 二、两根正交轴：整理状态 vs 身份争议

### 2.1 `research_status`（整理状态）

| 取值 | 含义 | 附加要求 |
|---|---|---|
| `uncompiled` | 未整理：本站尚未系统检索/录入 | 默认值，无需说明 |
| `searched` | 已检索未获：查过，但没有取得可核材料 | **必须**写 `research_note`（检索范围 + 结论）；建议写 `research_checked_at` |
| `compiled` | 已整理：有档案且断言逐条挂源 | 不等于"全部审核通过"；证据薄弱处仍须标 `evidence`/`status` |

- **移除**旧值 `disputed`：身份争议不是整理状态。写入 `research_status: disputed` 会**构建失败**。
- 迁移映射：旧 `disputed` → `research_status` 保持 `uncompiled`，同时 `disputed: true` + `dispute_note`。
- `research_checked_at`：`YYYY-MM-DD`，记录这次判断的日期，便于日后复算。

### 2.2 `disputed` + `dispute_note`（身份争议）

- `disputed: true` 表示"本站收录该人，但其**状元身份**存在异说"，**不表示此人是伪造人物**。
- `disputed: true` 必须带 `dispute_note`（既有守卫已强制），并继续参与"不派生同年边"的规则。
- 与 `research_status` 完全独立：一个人可以 `compiled` 且 `disputed`（档案整理得很好，但身份仍有异说）。

### 2.3 `dispute_claims`（断言级争议，v1 预留）

布尔值无法表达"哪一条断言存疑"。例如王维：《旧唐书》支持"进士及第"，"状元"只见笔记——存疑的是**夺魁**，不是**及第**。

```yaml
dispute_claims:
  - claim: 夺魁            # 夺魁｜进士及第｜名次｜生年｜卒年｜籍贯｜关系
    value: 721 年状元
    status: disputed       # confirmed｜disputed｜insufficient
    source_ids: [s0034]
    note: 正史仅作「进士擢第」，状元说见笔记
```

v1 **只定义结构，不要求现在填**；T06 迁移争议人物时按需启用。未填时前端继续用 `disputed` 布尔。

## 三、仕途四维：`career.highest / last / whereabouts / death`

### 3.1 字段

```yaml
career:
  # —— 旧字段：只读，不得据以推导下面四维 ——
  first_office / first_category / mid_office / mid_category
  final_office / final_category

  highest:        # 最高官
    status: recorded        # 可省，缺省=recorded
    office: 尚书右仆射
    category: 宰辅与执政     # 可选
    year: 991               # 与 year_label 二选一
    precision: exact        # exact｜circa｜range
    source_id: s0003
    note: 赠官不计
  last:           # 末任（最后一个实际官职）
    status: unknown
    note: 致仕前末任记载分歧，检索《宋史》本传与地方志未见确证
  whereabouts:    # 去向
    category: 归隐或讲学     # 归隐或讲学｜实业｜待核
    note: 致仕后主讲书院
    source_id: s0005
  death:          # 死亡
    category: 殉职或死事     # 殉职或死事｜早逝｜待核
    year: 1283
    precision: exact
    source_id: s0003
```

### 3.2 三态语义（本契约的核心）

| 数据形态 | 含义 | 前端应显示 |
|---|---|---|
| 字段**不存在** | **尚未迁移**（本站还没做这一维） | 「尚未整理」或留白，**不得**显示"无""不详" |
| `status: unknown` + `note` | **已检索未获**（做过，没找到） | 「已检索，未见记载」+ note |
| `status: recorded`（或省略 status） | **有值** | 正常展示，带来源与时间精度 |

**三者不可互相代替。** 缺字段不等于"没有这个官"，`unknown` 也不等于"没整理"。

### 3.3 校验规则（schema 强制）

- `status: unknown`：**禁止**同时写 `office`/`category`；**必须**写 `note`。
- `status: recorded`：至少要有 `office` 或 `category`。
- `year` 与 `year_label` **不能同时写**（避免两套时间口径并存）。
- `source_id` 必须是 `/^s\d{4}$/` 且存在（构建期校验引用）。
- `whereabouts.category` 只能是 `归隐或讲学 / 实业 / 待核`；`death.category` 只能是 `殉职或死事 / 早逝 / 待核`。
- **迁移期宽容**：`recorded` 但缺 `source_id` 只 **warn**，不阻断构建；T06 验收前必须补齐或改 `unknown`。

### 3.4 禁止事项

1. **不得从 `final_office` / `final_category` 自动生成任何一维**（构建期不写、测试有断言）。
2. 不得把事件标题（如"官至大理少卿"）直接当 `highest.office`，必须有独立判断与来源。
3. 不得用 `final_category: 宰辅` 反推 `highest`——旧分类是聚合口径，不是事实记录。
4. 不得为了"填满四维"把 `unknown` 改写成有值。

## 四、事件证据状态：`events[].evidence`

| 取值 | 含义 |
|---|---|
| `primary` | 已核原文/一手（正史列传、题名碑、殿试卷、墓志原文） |
| `secondary` | 二手转录（今人研究、企业史年表、方志整理本转引） |
| `pending` | 待证（无源或未核） |
| 缺省 | **不等于 primary**；缺 `source_id` 的事件按 `pending` 展示 |

- `evidence: primary` 但无 `source_id` → **构建失败**。
- `evidence: pending` 却挂了 `source_id` → **warn**（确认是"待证"还是"二手"）。
- 用途：T02 表 D 的 z0650 两条事件可标 `pending` 或 `secondary`，不再靠留空暗示。

## 五、兼容规则

| 场景 | 规则 |
|---|---|
| 旧深档（无 `career.highest` 等） | 原样可构建；四维计为 `missing` |
| 旧 `career.final_*` | 保留、只读；旧桑基/问答继续消费，不迁移 |
| 旧 `research_status` 缺省 | 读作 `uncompiled`，不推断 `compiled` |
| 旧 `research_status: disputed` | 已无合法数据；若出现即构建失败（按 §2.1 迁移） |
| `careers.yaml` 回填 | 只回填旧六字段；四维**不参与**回填，避免脚本挖掘值冒充考据结论 |
| `stats.json` | 升 **v5**：新增 `contract_version`、`career_facts`（四维 recorded/unknown/missing）、`research_status` 分布、`career_rows` |
| 消费方 | 读到未知字段应忽略；读到缺字段按 §3.2 三态处理，不得默认 `recorded` |

`career_facts` 的分母是 **656 名录**，不是 214 个有 career 记录者——避免"迁移了 10 人就显示 100%"。

## 六、构建期守卫（`scripts/build-data.ts` §7c）

**err（阻断构建，不写任何产物）**
1. `research_status: searched` 但缺 `research_note`
2. `research_status` 不是三态之一（zod）
3. `disputed: true` 缺 `dispute_note`（既有）
4. 四维 `source_id` 指向不存在的出处
5. 四维 `status: unknown` 却带值、或缺 `note`
6. `events[].evidence: primary` 无 `source_id`

**warn（记录但不阻断）**
1. `research_status != uncompiled` 但缺 `research_checked_at`
2. 四维 `recorded` 但无 `source_id`
3. `events[].evidence: pending` 却挂了 `source_id`

| 10 | z0004 | 员半千 | 存疑 + 既有 bio 自相矛盾，验证不改旧断言也能补四维 |

### 7.2 每人交付要求

1. **四格齐全**：`highest` / `last` / `whereabouts` / `death` 各给一条结论，不允许留空。
2. `recorded` 格：`office` 或 `category` + 时间（`year` 或 `year_label` 择一，`precision` 标 `circa`/`range`）+ `source_id`。
3. `unknown` 格：`status: unknown` + `note` 写**检索范围**（查了哪本书/哪个库、结论是什么），不写"无资料"三个字了事。
4. **不得**从 `final_*` 推导；不得把旧分类换个词填进去。
5. 事件逐条补 `evidence`；`pending` 不挂假源。
6. `research_status` 同步：整理完的写 `compiled` 或 `searched`（配 `research_note` + `research_checked_at`）。
7. 一人一文件改动，构建必须通过；`stats.career_facts` 的增量要与预期一致（10 人 × 4 格）。

### 7.3 验收口径

- 40 格逐格有状态，`recorded` 格全部有 `source_id`，`unknown` 格全部有 `note`；
- 构建 `test:data` 全绿，`stats.career_facts.*.recorded` 之和等于实际 `recorded` 格数；
- 抽 3 人回读页面，确认三态显示不同（有值 / 已检索未见 / 尚未整理）。
